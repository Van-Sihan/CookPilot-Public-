AudioWorklet 이란 무엇인가

물어본 것 — “audio worklet 이란 뭐야?”

브라우저에서 소리만 따로 처리하는 일꾼을 만드는 방법입니다. 이 문서를 다 읽고 나면 화면 쓰레드와 소리 쓰레드가 왜 나뉘어 있는지, 마이크에서 나온 소리가 어떤 모양으로 바뀌어 제미나이까지 가는지 알게 됩니다. public/audio/pcm-worklet.js 와 lib/adapter/browser-audio.ts 를 읽습니다.

1부 · 기본 문법

먼저, 쓰레드가 하나라는 것부터

자바스크립트는 기본적으로 쓰레드가 하나뿐입니다. 쓰레드란 일을 처리하는 일꾼 한 명이라고 보면 됩니다. 일꾼이 한 명이니 한 번에 한 가지 일만 합니다.

그래서 이런 코드를 브라우저에서 돌리면 화면이 3초 동안 얼어붙습니다.

// 3초 동안 쉬지 않고 도는 계산
const end = Date.now() + 3000;
while (Date.now() < end) {
  // 아무것도 안 하고 그냥 시간만 보낸다
}

console.log("끝났다");

이 3초 동안에는 단추를 눌러도 반응이 없습니다. 일꾼이 계산에 매달려 있어서 클릭을 처리할 짬이 없기 때문입니다.

소리에는 이게 치명적입니다

화면은 잠깐 멈춰도 사람이 "느리네" 하고 넘어갑니다. 그런데 소리는 다릅니다. 소리는 초당 정해진 개수만큼 끊김 없이 흘러가야 합니다. 한 번이라도 늦으면 "뚝" 하고 잡음이 납니다.

여기서 AudioWorklet이 나옵니다. AudioWorklet 은 소리 전용 쓰레드에서 도는 작은 프로그램입니다. 화면을 그리는 일꾼과 따로 놀기 때문에, 화면이 버벅여도 소리는 안 끊깁니다.

예전에는 ScriptProcessorNode 라는 것을 썼습니다. 이건 화면 쓰레드에서 돌았습니다. 그래서 화면이 바쁘면 소리가 끊겼습니다. AudioWorklet 은 그 문제를 고치려고 나온 후속 기능입니다.

아주 작은 예제

AudioWorklet 은 항상 파일 두 개로 나뉩니다. 하나는 소리 쓰레드에서 돌 코드, 하나는 그것을 불러 쓰는 화면 쪽 코드입니다.

먼저 소리 쓰레드에서 돌 파일입니다.

// my-worklet.js — 소리 전용 쓰레드에서 돈다
class MyProcessor extends AudioWorkletProcessor {
  process(inputs) {
    // inputs[0][0] 이 마이크에서 온 소리 한 토막이다
    const input = inputs[0][0];

    // false 를 주면 일꾼이 죽는다. 계속 살리려면 true
    return true;
  }
}

// 화면 쪽에서 이 이름으로 부른다
registerProcessor("my-processor", MyProcessor);

다음은 화면 쪽에서 이 일꾼을 세우는 코드입니다.

// 소리를 다루는 판을 하나 만든다
const ctx = new AudioContext();

// 위 파일을 소리 쓰레드에 올린다. 주소로 부른다
await ctx.audioWorklet.addModule("/my-worklet.js");

// 올린 일꾼을 실제로 세운다. 이름은 registerProcessor 에 적은 그것
const node = new AudioWorkletNode(ctx, "my-processor");

addModule 은 주소를 받습니다. 그래서 워크릿 파일은 import 로 가져올 수 없습니다. 번들에 섞이면 주소가 없어지기 때문입니다. 쿡파일럿이 이 파일만 public/ 에 따로 둔 까닭이 이것입니다.

process 는 얼마나 자주 불릴까

process 는 128칸마다 한 번씩 불립니다. 칸이란 소리를 잘게 쪼갠 한 조각입니다.

16000Hz 로 소리를 받는다면 1초에 16000칸이 들어옵니다. 128칸마다 부르니 1초에 125번 불리는 셈입니다. 이 숫자가 뒤에서 중요해집니다.

2부 · 우리 코드에서는

쿡파일럿은 요리하는 동안 마이크를 열어 두고 제미나이와 말을 주고받습니다. 그 소리 길의 시작이 AudioWorklet 입니다.

소리 쓰레드에서 도는 일꾼

public/audio/pcm-worklet.js

class PcmCollector extends AudioWorkletProcessor {
  constructor() {
    super();

    this.chunk = 1024;

    // 아직 다 못 채운 소리를 모아 두는 자리
    this.buffer = new Float32Array(this.chunk);

    // 지금까지 몇 칸이 찼는지
    this.filled = 0;
  }

this.chunk = 1024 가 이 파일의 핵심입니다. 128칸이 올 때마다 곧바로 보내지 않고, 1024칸이 모일 때까지 기다렸다가 한 번에 보냅니다.

왜 그럴까요. 파일에 적힌 까닭 그대로입니다 — 128칸마다 보내면 1초에 125번 메시지를 보내게 되어 낭비가 큽니다. 1024칸이면 16kHz 기준 64밀리초쯤이라, 사람이 느끼기에는 곧바로입니다.

이어서 실제로 소리를 옮겨 담는 부분입니다.

public/audio/pcm-worklet.js:29

  process(inputs) {
    // 첫 번째 입력의 첫 번째 채널. 마이크는 보통 한 채널이다
    const input = inputs[0] && inputs[0][0];

    // 마이크가 잠깐 끊기면 빈 값이 온다. 그래도 일꾼은 살아 있어야 한다
    if (!input) return true;

    for (let i = 0; i < input.length; i += 1) {
      this.buffer[this.filled] = input[i];
      this.filled += 1;

      // 다 찼으면 본 화면으로 보내고 자리를 비운다
      if (this.filled === this.chunk) {
        this.port.postMessage(this.buffer.slice(0));
        this.filled = 0;
      }
    }

    return true;
  }

this.port.postMessage 가 소리 쓰레드에서 화면 쓰레드로 값을 건네는 통로입니다. 두 쓰레드는 변수를 함께 쓸 수 없어서, 이렇게 메시지로만 주고받습니다.

this.buffer 를 그대로 보내지 않고 .slice(0) 로 복사본을 보냅니다. 원본을 보내면 다음 소리를 담는 동안 받는 쪽이 그 자리를 읽고 있어서 값이 뒤섞입니다. 초보자가 놓치기 가장 쉬운 지점입니다.

화면 쪽에서 일꾼을 세우는 곳

lib/adapter/browser-audio.ts:90

// 16kHz 로 달라고 못 박는다. 브라우저가 맞춰 준다
const ctx = new AudioContext({ sampleRate: INPUT_RATE });

try {
  // 소리 전용 쓰레드에 일꾼을 올린다. 파일을 못 찾으면 여기서 터진다
  await ctx.audioWorklet.addModule(WORKLET_URL);
} catch {
  // 일꾼을 못 올렸으면 마이크를 놓아 주고 물러난다
  stream.getTracks().forEach((t) => t.stop());
  void ctx.close();
  return { ok: false, problem: "failed" };
}

sampleRate: INPUT_RATE 는 16000 입니다. browser-audio.ts:13 에 그렇게 적혀 있습니다. 이 숫자를 여기서 못 박아 두면 브라우저가 알아서 16kHz 로 바꿔 줍니다. 우리가 직접 칸을 솎아 내면 소리가 거칠어지고 코드도 길어집니다.

왜 하필 16000이냐면, 제미나이 라이브가 그렇게 정해 두었기 때문입니다. 받는 쪽은 16kHz, 보내 주는 쪽은 24kHz 입니다.

소리 장치를 잇는 모양

lib/adapter/browser-audio.ts:105

// 마이크에서 오는 소리를 이 장치 안으로 끌어들이는 입구
const source = ctx.createMediaStreamSource(stream);

// 아까 올린 일꾼을 실제로 세운다
const node = new AudioWorkletNode(ctx, "pcm-collector");

// 소리 크기를 재는 저울. 막대 그림에만 쓴다
const meter = ctx.createAnalyser();

// 마이크를 일꾼과 저울 양쪽에 잇는다. 스피커에는 잇지 않는다
source.connect(node);
source.connect(meter);

소리 장치들은 이렇게 선으로 잇는 방식으로 씁니다. 마이크(source)에서 나온 소리가 일꾼(node)과 저울(meter) 두 갈래로 흘러갑니다.

저울을 따로 둔 까닭이 주석에 적혀 있습니다 — 보내는 소리와 그리는 소리를 같은 길로 뽑으면 한쪽이 막힐 때 둘 다 멈춥니다.

바로 다음 줄에 눈여겨볼 것이 하나 더 있습니다.

lib/adapter/browser-audio.ts:122

/* 크롬은 아무 데도 안 이어진 워크릿을 쉬게 만들 때가 있다.
   소리가 0인 곳으로 이어 두면 계속 돌면서도 스피커로는 아무것도 안 나간다 */
const mute = ctx.createGain();
mute.gain.value = 0;
node.connect(mute).connect(ctx.destination);

일꾼이 만든 소리를 스피커로 내보내고 싶지는 않습니다. 내보내면 자기 목소리가 되울립니다. 그렇다고 아무 데도 안 이으면 크롬이 일꾼을 재워 버립니다.

그래서 소리 크기를 0으로 만든 장치를 하나 끼워 스피커까지 이어 둡니다. 길은 이어져 있지만 아무 소리도 안 나갑니다.

받은 소리를 제미나이가 아는 모양으로

lib/adapter/browser-audio.ts:136

node.port.onmessage = (e: MessageEvent<Float32Array>) => {
  // -1~1 짜리 소수를 16비트 정수로 옮긴다
  const pcm = floatToPcm16(e.data);

  // 나중에 통째로 WAV 를 만들 수 있게 챙겨 둔다
  kept.push(pcm);

  // 실시간으로 보내는 쪽이 걸어 둔 손이 있으면 바로 넘긴다
  hand?.(pcm);
};

워크릿이 보낸 값은 Float32Array 입니다. -1 과 1 사이의 소수가 1024개 들어 있습니다. 그런데 제미나이는 16비트 PCM 을 받습니다. PCM 은 소리를 정수 목록으로 적어 둔 가장 단순한 형식입니다.

그 변환이 floatToPcm16 입니다.

lib/adapter/browser-audio.ts:199

/* 마이크가 세면 1을 넘는 값이 온다. 그대로 곱하면 값이 넘쳐서
   가장 큰 소리가 가장 작은 소리로 뒤집힌다. 그래서 먼저 잘라 낸다 */
const clamped = Math.max(-1, Math.min(1, input[i]));

// 음수 쪽이 한 칸 더 넓어서 곱하는 수가 다르다
out[i] = clamped < 0 ? clamped * 0x8000 : clamped * 0x7fff;

음수와 양수에 곱하는 수가 다릅니다. 16비트 정수는 -32768(0x8000)부터 32767(0x7fff)까지라 음수 쪽이 한 칸 더 넓습니다. 양쪽에 32767을 곱하면 가장 낮은 소리에서 값이 어긋납니다.

전체 길을 한 줄로

지금까지 본 것을 이으면 이렇게 됩니다.

마이크
  → getUserMedia (권한 창)
  → AudioContext (16kHz 로 못 박음)
  → AudioWorklet 'pcm-collector'   ← 소리 전용 쓰레드
  → postMessage (1024칸씩)
  → floatToPcm16 (소수 → 16비트 정수)
  → gemini-live-gateway 가 웹소켓으로 전송

AudioWorklet 은 이 길의 세 번째와 네 번째 칸을 맡습니다. 마이크에서 나온 날것의 소리를 받아, 보내기 좋은 크기로 모아 주는 일입니다.

3부 · 직접 확인해보기

실험 1 — 모으는 크기를 바꿔 보기

public/audio/pcm-worklet.js 의 this.chunk 를 1024 에서 128 로 바꾸고 npm run dev 로 요리 화면에 들어가 보세요.

브라우저 개발자 도구(F12)의 콘솔에서 메시지가 훨씬 자주 오가는 것을 볼 수 있습니다. 반대로 16384 로 키우면 1초쯤 뭉쳐서 오기 때문에 말하고 나서 반응이 늦어집니다. 왜 1024를 골랐는지가 몸으로 느껴집니다.

실험 2 — 복사본을 안 보내면 어떻게 되는지

같은 파일에서 this.port.postMessage(this.buffer.slice(0)) 를 this.port.postMessage(this.buffer) 로 바꿔 보세요.

.slice(0) 하나를 뺐을 뿐인데 소리가 지직거리기 시작합니다. 다음 소리를 담는 동안 받는 쪽이 같은 자리를 읽어서 값이 섞이기 때문입니다. 확인했으면 반드시 되돌려 놓으세요.

실험 3 — 일꾼을 죽여 보기

process 의 마지막 return true 를 return false 로 바꿔 보세요.

마이크를 켜자마자 소리 수집이 딱 한 번 만에 멈춥니다. false 는 "이 일꾼 이제 필요 없다"는 뜻이라 브라우저가 정리해 버립니다.

실험 4 — 음소거 장치를 빼 보기

lib/adapter/browser-audio.ts 에서 mute.gain.value = 0; 을 1 로 바꾸면 자기 목소리가 스피커로 그대로 되돌아옵니다. 왜 0으로 두었는지를 귀로 확인할 수 있습니다.

헷갈리기 쉬운 점

워크릿 안에서는 window 도 document 도 없습니다. 화면 쓰레드가 아니기 때문입니다. console.log 는 되지만 화면을 만지려 들면 오류가 납니다. 값을 바깥으로 내보내려면 반드시 postMessage 를 써야 합니다.

addModule 은 기다려야 합니다. await 를 빼고 곧바로 new AudioWorkletNode(...) 를 부르면 "그런 이름의 일꾼이 없다"는 오류가 납니다. 파일을 다 읽어 등록하기 전이기 때문입니다.

registerProcessor 의 이름과 AudioWorkletNode 의 이름이 같아야 합니다. 우리 코드에서는 양쪽 다 "pcm-collector" 입니다. 한쪽만 고치면 조용히 안 됩니다.

마이크는 https 에서만 열립니다. localhost 는 예외로 허용됩니다. 그래서 개발할 때는 잘 되다가 다른 기기에서 http 로 열면 갑자기 안 됩니다. browser-audio.ts:68 이 그 상황을 "missing" 으로 구분해 둔 까닭입니다.
