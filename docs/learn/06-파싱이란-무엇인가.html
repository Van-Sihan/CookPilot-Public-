파싱이란 무엇인가 — 냉장고에 적은 글이 재료 목록이 되기까지

물어본 것 — “기능명세서 FN05 의 ‘재료를 최대 20개로 파싱하고 2개 미만이면 거절한다. 1단계에서 후보 목록을 받아 유효 항목만 5개까지 수집한다. 2단계에서 보유 재료를 다시 전달해 레시피를 생성한다.’ 이게 무슨 뜻이야? 파싱한다?”

파싱(parsing) 은 사람이 편하게 쓴 글자 뭉치를, 프로그램이 다룰 수 있는 모양으로 바꾸는 일입니다. "계란, 파, 김치 있어요" 라는 글자 하나를 ["계란", "파", "김치"] 라는 목록으로 바꾸는 것이 파싱입니다. 이 문서를 다 읽으면 왜 이 단계가 필요한지, 왜 20개에서 자르고 2개 미만은 거절하는지, 냉장고 추천이 왜 두 걸음으로 나뉘어 있는지, 그리고 이 검사들이 왜 하필 lib/domain/ 에 있는지 알게 됩니다.

1부 · 기본 문법

문자열과 배열은 다른 물건입니다

먼저 이 둘의 차이를 몸으로 알아야 파싱이 왜 필요한지 보입니다.

문자열(string) 은 글자들이 한 줄로 이어 붙은 값입니다. 따옴표로 감싸서 씁니다. 컴퓨터가 보기에 이것은 덩어리 하나입니다.

const memo = "계란, 파, 김치";

// 길이를 물어보면 "재료 3개" 가 아니라 "글자 9개" 라고 답한다
console.log(memo.length); // 9

// 첫 번째를 꺼내 보면 "계란" 이 아니라 글자 하나가 나온다
console.log(memo[0]); // "계"

사람 눈에는 재료가 셋으로 보이지만, 프로그램에게는 그냥 글자 아홉 개입니다. 쉼표도 그저 글자 하나일 뿐, “여기서 나누라” 는 뜻이 아닙니다.

배열(array) 은 값 여러 개를 순서대로 담는 상자입니다. 대괄호로 씁니다.

const items = ["계란", "파", "김치"];

console.log(items.length); // 3  ← 이번엔 재료 개수다
console.log(items[0]);     // "계란"  ← 재료 하나가 통째로 나온다

// 하나씩 꺼내 볼 수 있다
for (const it of items) console.log(it);

차이가 분명합니다. 배열이어야 “몇 개인지 세기”, “하나씩 꺼내기”, “일부만 잘라 쓰기” 가 됩니다. 문자열로는 이 중 어느 것도 못 합니다.

그래서 사용자가 친 글을 받으면, 쓰기 전에 배열로 바꿔 두어야 합니다. 이 “바꾸는 일” 이 바로 파싱입니다.

split — 글자를 기준 삼아 자르기

문자열에는 split 이라는 기능이 붙어 있습니다. 기준 글자를 주면 그 자리에서 잘라 배열로 돌려줍니다.

const memo = "계란,파,김치";

const items = memo.split(",");
console.log(items); // ["계란", "파", "김치"]

그런데 사람은 이렇게 얌전히 적지 않습니다. 쉼표 뒤에 빈칸을 넣기도 하고, 줄을 바꿔 적기도 하고, 가운뎃점을 쓰기도 합니다. 기준을 하나만 정하면 이런 글이 통째로 재료 하나가 되어 버립니다.

"계란, 파\n김치".split(",");
// ["계란", " 파\n김치"]   ← 줄바꿈은 안 잘렸고, 앞에 빈칸도 남았다

여러 기준으로 자르기 — 정규식

정규식(정규표현식) 은 “이런 모양의 글자” 를 적는 문법입니다. 슬래시 두 개 사이에 씁니다. split 에 정규식을 주면 여러 종류의 구분자를 한꺼번에 처리할 수 있습니다.

// [ ] 안은 "이 중 아무거나", + 는 "하나 이상 연달아"
const items = "계란, 파\n김치·두부".split(/[,\n·]+/);
console.log(items); // ["계란", " 파", "김치", "두부"]

아직 " 파" 앞에 빈칸이 남아 있습니다. 이런 뒷정리는 보통 두 단계를 더 거칩니다.

const items = "계란, 파\n김치, , 두부"
  .split(/[,\n·]+/)
  // map: 모든 칸에 같은 손질을 한 번씩 한다. trim 은 앞뒤 빈칸 떼기
  .map((s) => s.trim())
  // filter: 조건에 맞는 것만 남긴다. 빈 칸은 버린다
  .filter((s) => s.length > 0);

console.log(items); // ["계란", "파", "김치", "두부"]

split → map → filter. 이 세 걸음이 가장 흔한 파싱 모양입니다. 자르고, 다듬고, 걸러 냅니다.

slice — 앞에서 몇 개만 떼어 오기

const many = ["가", "나", "다", "라", "마"];

// 앞에서 3개만. 원래 배열은 그대로 남는다
console.log(many.slice(0, 3)); // ["가", "나", "다"]

// 개수가 모자라도 에러가 나지 않는다. 있는 만큼만 준다
console.log(["가"].slice(0, 3)); // ["가"]
알아두면 좋은 것

“파싱” 이라는 말은 재료 나누기에만 쓰는 말이 아닙니다. 정해진 모양이 아닌 입력을 읽어 구조를 뽑아내는 일을 통틀어 그렇게 부릅니다. 주소에서 도메인만 뽑는 것도 파싱이고, JSON 글자를 객체로 바꾸는 JSON.parse 도 이름 그대로 파싱입니다.

2부 · 우리 코드에서는

① 재료 파싱 — readFridgeItems

사용자는 /pick 화면의 여러 줄 입력칸에 냉장고 사정을 자유롭게 적습니다. 그 글자를 재료 배열로 바꾸는 함수가 이것입니다. 1부에서 본 split → map → filter 가 그대로 나옵니다.

lib/domain/recipe.ts:428-440 
export function readFridgeItems(raw: string): FridgeRead {
  const text = raw.trim();

  if (text.length === 0) return { ok: false, problem: "empty" };

  const items = text
    // 쉼표·줄바꿈·가운뎃점·슬래시를 모두 칸막이로 본다
    .split(/[,\n·/]+/)
    .map((s) => s.trim())
    // 빈 칸과 지나치게 긴 것은 버린다. 긴 것은 재료가 아니라 문장이다
    .filter((s) => s.length > 0 && s.length <= 30);

한 줄씩 봅니다.

  • raw: string — 들어오는 것은 글자 하나입니다. 아직 목록이 아닙니다.
  • FridgeRead — 돌려주는 것은 목록이 아니라 “읽어 본 결과” 입니다. 성공했을 수도, 거절했을 수도 있기 때문입니다. 뒤에서 다시 봅니다.
  • split(/[,\n·/]+/) — 네 가지를 칸막이로 봅니다. 쉼표, 줄바꿈, 가운뎃점, 슬래시입니다. 사람마다 적는 방식이 달라서 하나만 받으면 "두부 계란 김치" 가 재료 하나로 들어옵니다.
  • s.length <= 30 — 30자가 넘으면 버립니다. 왜 그런지가 중요합니다. 30자짜리 “재료” 는 없습니다. 그건 "어제 사 온 소고기가 좀 남았는데요" 같은 문장입니다. 문장을 재료 이름이라며 모델에게 넘기면 엉뚱한 답이 옵니다.

② 2개 미만이면 거절 — 'too-few'

lib/domain/recipe.ts:443-448 
  // 하나만 적으면 만들 수 있는 요리가 너무 넓어진다
  if (items.length < MIN_FRIDGE_ITEMS) return { ok: false, problem: "too-few" };

  // 스무 가지를 넘기면 물음이 길어지기만 하고 답이 나아지지 않는다

MIN_FRIDGE_ITEMS 는 같은 파일 :418 에 2 로 적혀 있습니다.

왜 2개 미만을 거절할까요. “계란” 하나만 적으면 만들 수 있는 요리가 수천 가지입니다. 모델은 그중 아무거나 고를 것이고, 사용자는 왜 그게 나왔는지 알 수 없습니다. 그러면 “냉장고를 부탁해” 라는 기능 자체가 의미를 잃습니다. 받아 봐야 쓸모없는 답이 올 것이 뻔한 요청은 아예 보내지 않습니다. 요청 한 번은 시간도 걸리고 사용자 지갑의 API 요금도 씁니다.

왜 20개에서 자를까요. 반대 이유입니다. 재료를 40개 적으면 모델에게 보내는 질문이 그만큼 길어집니다. 그런데 답이 두 배 좋아지지는 않습니다. 요리 하나에 실제로 쓰이는 재료는 대여섯 개이기 때문입니다. 길이는 늘고 답은 그대로면 손해만 남습니다. 그래서 위를 막아 둡니다.

알아두면 좋은 것 · 왜 배열을 그냥 돌려주지 않을까

readFridgeItems 는 string[] 대신 { ok: true, items } 또는 { ok: false, problem } 를 돌려줍니다. 이런 모양을 결과 타입 이라고 합니다. 빈 배열을 돌려주면 “아무것도 안 적었다” 와 “하나만 적었다” 를 구별할 수 없습니다. 까닭이 다르면 화면이 할 말도 달라야 하므로 problem 에 이유를 실어 보냅니다. 다만 한국어 문장은 여기 없습니다. "empty", "too-few" 라는 낱말만 있고, 무슨 말로 보여 줄지는 화면이 정합니다.

③ 왜 1단계 / 2단계로 나눴는가

재료 파싱이 끝나면 이제 모델에게 물어볼 차례입니다. 그런데 쿡파일럿은 여기서 한 번에 레시피를 받지 않습니다. 두 걸음으로 나눕니다.

1단계 — 후보만 받아 옵니다. 레시피가 아니라 요리 이름 목록입니다.

lib/usecase/plan-recipe.ts:213-229 
export async function findFridgeIdeas(
  raw: string,
  servings: number,
  gateway: RecipeGateway,
): Promise<IdeaResult> {
  const read = readFridgeItems(raw);

  // 재료가 모자라면 다녀올 것도 없다
  if (!read.ok) return { ok: false, reason: read.problem };

  const answer = await gateway.fridgeIdeas(read.items, clampServings(servings));

  return answer.ok ? { ok: true, ideas: answer.ideas } : { ok: false, reason: answer.reason };
}
  • readFridgeItems(raw) — ①에서 본 파싱을 먼저 합니다.
  • if (!read.ok) return ... — 거절이면 모델을 아예 부르지 않고 끝냅니다. 주석에도 “재료가 모자라면 다녀올 것도 없다” 라고 적혀 있습니다.
  • await gateway.fridgeIdeas(...) — 여기서 모델에 다녀옵니다. await 는 “답이 올 때까지 이 줄에서 기다린다” 는 뜻입니다.

이 함수는 아무것도 저장하지 않습니다. 같은 파일 :206-208 에 까닭이 적혀 있습니다 — 아직 사람이 고른 요리가 없기 때문입니다. 여기서 저장해 버리면 사용자가 고르지도 않은 요리가 장보기 화면에 앉아 있게 됩니다.

2단계 — 사용자가 하나를 고른 뒤에야 레시피를 만듭니다.

④ “유효 항목만 수집한다” — 모델 응답도 파싱합니다

지금까지는 사람이 친 글을 파싱했습니다. 그런데 파싱이 한 번 더 있습니다. 모델이 보낸 답도 파싱합니다.

모델은 “JSON 으로 답하라” 고 시켜도 한 번씩 어깁니다. 칸 하나를 빼먹거나, 숫자 자리에 글자를 넣거나, 목록 안에 엉뚱한 값을 섞습니다. 그것을 그대로 화면에 넘기면 화면이 깨집니다. 그래서 받아 온 값을 한 줄씩 검사해서 통과한 것만 모읍니다. 명세서의 “유효 항목만 수집한다” 가 이 뜻입니다.

lib/domain/recipe.ts:487-504 
export function readFridgeIdeas(value: unknown): readonly FridgeIdea[] {
  // 배열이 아니면 고를 것이 없다
  if (!Array.isArray(value)) return [];

  const ideas: FridgeIdea[] = [];

  for (const raw of value) {
    if (typeof raw !== "object" || raw === null) continue;

    const bag = raw as Record<string, unknown>;
    const title = asText(bag.title);

    // 이름 없는 후보는 화면에 뭘 적을지 알 수 없다
    if (title.length === 0) continue;
  • value: unknown — unknown 은 “무엇이 올지 모른다” 는 타입입니다. 타입스크립트는 unknown 값을 확인 없이는 못 쓰게 막습니다. 모델 응답에 딱 맞는 타입입니다. 정직하게 “모른다” 고 적어 두는 것입니다.
  • Array.isArray(value) — 배열인지부터 봅니다. 아니면 빈 목록을 돌려줍니다.
  • continue — 이 줄만 건너뛰고 다음 줄로 갑니다. 한 후보가 이상하다고 전체를 버리지 않습니다. 후보는 어차피 여럿이라 하나가 빠져도 나머지 중에서 고르면 됩니다.

나머지 칸은 없어도 살려 둡니다. 다만 지어내지는 않습니다.

  return ideas;
}
  • asMinutes(bag.minutes) ?? 0 — 시간을 못 읽으면 0 입니다. ?? 는 “왼쪽이 없으면 오른쪽” 이라는 뜻입니다. :509-510 의 주석대로 지어낸 숫자를 적는 것보다 낫습니다. 0 이면 화면이 시간 줄을 빼면 됩니다.
  • missing — 배열이 아니면 빈 배열로 둡니다. 빈 배열은 “가진 재료만으로 됩니다” 라는 뜻이 되어, 고를 때 가장 힘이 되는 정보입니다.
  • break — MAX_IDEAS(:477 에 5) 개가 차면 반복을 아예 멈춥니다. 명세서의 “5개까지 수집한다” 가 이 줄입니다. 모델이 열 개를 보내도 다섯 개만 씁니다.
왜 모델 응답을 그대로 믿지 않는가

모델은 우리 코드가 아닙니다. 버전이 올라가면 답하는 버릇도 바뀝니다. 같은 요청에 매번 조금씩 다르게 답하기도 합니다. 우리가 통제할 수 없는 값이라는 뜻입니다.

통제할 수 없는 값이 화면까지 그대로 흘러가면, 언젠가 사용자가 불 앞에서 깨진 화면을 보게 됩니다. lib/domain/recipe.ts:8-9 에 그 이유가 적혀 있습니다. 검사는 “모델을 의심해서” 가 아니라 바깥에서 온 값은 다 검사한다는 원칙입니다. 사용자 입력을 검사하는 것과 똑같은 일입니다.

⑤ 왜 이 검사가 lib/domain/ 에 있는가

이 저장소는 클린 아키텍처 를 따릅니다. 코드를 네 겹으로 나누고 바깥이 안쪽을 가져다 쓰게만 하는 방식입니다.

도메인  →  유스케이스  →  어댑터  →  화면
(규칙)     (일의 순서)    (제미나이)   (React)

화살표는 "이쪽이 저쪽을 안다" 가 아니라 "이쪽을 저쪽이 가져다 쓴다" 방향
  • 도메인 lib/domain/recipe.ts — “재료란 무엇이고 몇 개부터 쓸모가 있는가”. 규칙만 압니다.
  • 유스케이스 lib/usecase/plan-recipe.ts — “재료를 읽고, 후보를 받고, 저장한다”. 일의 순서를 압니다.
  • 어댑터 lib/adapter/gemini-recipe-gateway.ts — 제미나이에 실제로 다녀옵니다.
  • 화면 components/pick/pick-cards.tsx — 버튼과 카드를 그립니다.

“2개 미만이면 거절” 은 어느 겹의 지식일까요. 이것은 화면 사정도, 제미나이 사정도 아닙니다. “재료 하나로는 요리를 좁힐 수 없다” 는 요리라는 일 자체의 성질입니다. 그래서 도메인에 둡니다.

도메인에 두면 얻는 것이 구체적으로 있습니다.

  • 한 군데만 고치면 됩니다. 최소 개수를 3으로 바꾸려면 lib/domain/recipe.ts:418 의 숫자 하나만 고칩니다. 1단계와 2단계 둘 다 같은 함수를 부르므로 자동으로 같이 바뀝니다. 화면에 흩어 놨다면 세 군데를 찾아 고치다 한 군데를 빠뜨립니다.
  • 화면이 바뀌어도 규칙은 남습니다. 나중에 앱이나 서버에서 같은 기능을 만들어도 readFridgeItems 를 그대로 부르면 됩니다. 이 파일에는 React 도 fetch 도 window 도 없기 때문입니다.
  • 시험하기 쉽습니다. 글자를 넣고 결과를 보는 함수라 브라우저 없이 그 자리에서 확인할 수 있습니다.

반대로 도메인에 없는 것도 분명합니다. lib/domain/recipe.ts 어디에도 “재료를 두 개 이상 적어 주세요” 라는 한국어 문장이 없습니다. "too-few" 라는 낱말만 있습니다. 무슨 말로 보여 줄지는 화면의 몫이기 때문입니다. 도메인이 한국어를 쥐고 있으면 나중에 다른 말로 바꿀 수 없습니다.

3부 · 직접 확인해보기

실험 1 · 파싱이 실제로 어떻게 자르는지 눈으로 보기

npm run dev 로 띄우고 /pick 을 엽니다. 개발자 도구(F12) → Console 탭에 아래를 그대로 붙여 넣고 실행해 보세요. readFridgeItems 안의 파싱과 같은 코드입니다.

"계란, 파\n김치·두부//대파".split(/[,\n·/]+/)
  .map(s => s.trim())
  .filter(s => s.length > 0 && s.length <= 30)

다섯 개짜리 배열이 나옵니다. 이번엔 .split(...) 부분을 지우고 문자열만 남겨서 .length 를 찍어 보세요. 재료 개수가 아니라 글자 개수가 나옵니다. 1부에서 본 차이입니다.

실험 2 · 'too-few' 를 직접 만나 보기

/pick 의 냉장고 입력칸에 “계란” 하나만 적고 버튼을 눌러 보세요. 모델에 다녀오지 않고 즉시 안내가 뜹니다. 개발자 도구의 Network 탭을 켜 두면 generativelanguage.googleapis.com 으로 나가는 요청이 하나도 없다는 것을 확인할 수 있습니다.

이번엔 “계란, 파” 처럼 두 개를 적어 보세요. 이제 요청이 나갑니다. lib/usecase/plan-recipe.ts:222 의 if (!read.ok) return 한 줄이 만드는 차이입니다.

실험 3 · 최소 개수를 바꿔 보기

lib/domain/recipe.ts:418 의 MIN_FRIDGE_ITEMS 를 2 에서 4 로 고치고 저장하세요. 화면이 저절로 새로 고쳐집니다. 이제 재료를 셋만 적어도 거절당합니다.

여기서 확인할 것 — 화면 파일은 한 줄도 안 고쳤습니다. 1단계와 2단계 둘 다 같이 바뀝니다. ⑤ 에서 말한 “한 군데만 고치면 된다” 를 직접 겪는 것입니다. 확인했으면 2 로 되돌리세요.

실험 4 · 일부러 고장 내서 에러 보기

lib/domain/recipe.ts:440 의 .filter((s) => ...) 에서 filter 를 filtr 로 오타를 내 보세요. 에디터에 빨간 줄이 뜨고 터미널에 이런 메시지가 나옵니다.

Property 'filtr' does not exist on type 'string[]'.
  Did you mean 'filter'?

“string[](문자열 배열)에 filtr 이라는 것은 없다” 는 뜻입니다. 타입스크립트가 실행하기 전에 잡아 준 것입니다.

다음은 더 재미있는 실험입니다. :435 의 const items = text 에서 .split(...) 줄만 지워 보세요. 이번엔 Property 'map' does not exist on type 'string' 이라고 합니다. 문자열에는 map 이 없기 때문입니다. “파싱을 먼저 해야 목록으로 다룰 수 있다” 를 타입스크립트가 그대로 말해 주는 것입니다. 확인했으면 되돌리세요.

실험 5 · 두 걸음이 나뉘어 있음을 확인하기

Network 탭을 켜고 재료를 서너 개 적어 후보 찾기를 실행하세요. 요청이 한 번 나가고 후보 카드가 뜹니다. 카드가 뜬 뒤에도 더 이상 요청이 없다는 것을 확인하세요.

이제 카드 하나를 누릅니다. 그때 두 번째 요청이 나갑니다. 그 요청의 Payload 를 열어 보면 고른 요리 이름과 함께 내가 적은 재료가 다시 들어 있습니다. lib/usecase/plan-recipe.ts:247 에서 readFridgeItems 를 다시 부르는 그 값입니다.

헷갈리기 쉬운 점

1. 파싱은 “검사” 가 아니라 “변환” 이 본업입니다. 글자를 목록으로 바꾸는 것이 먼저이고, 바꾸는 김에 이상한 것을 걸러 내는 것입니다. 두 일이 한 함수 안에 있어서 섞여 보이지만 목적이 다릅니다.

2. "계란" 과 ["계란"] 은 다른 값입니다. 앞은 글자 두 개짜리 문자열, 뒤는 원소 한 개짜리 배열입니다. .length 를 물어보면 각각 2 와 1 이 나옵니다. 이 둘을 헷갈리면 개수를 세는 코드가 조용히 틀립니다.

3. “유효 항목만 수집한다” 는 “전부 아니면 전무” 가 아닙니다. 후보 다섯 중 하나가 이상하면 그 하나만 버리고 넷을 씁니다 (continue). 반면 readRecipe 는 재료가 하나도 안 남으면 레시피 전체를 거절합니다(:169). 부분이 빠져도 되는 것과 안 되는 것을 구분한 결과입니다. 후보는 여럿 중 고르면 되지만, 재료 없는 레시피는 쓸 수가 없습니다.

4. 20개와 5개는 자르는 대상이 다릅니다. items.slice(0, 20) 은 사람이 적은 재료를 자릅니다. MAX_IDEAS 의 5는 모델이 보낸 후보를 자릅니다. 명세서 한 문장에 나란히 있어서 같은 것으로 보이지만 전혀 다른 자리입니다.

5. 2단계에서 재료를 다시 넘기는 것은 실수가 아닙니다. “1단계에서 이미 보냈는데 왜 또 보내지?” 싶지만, 모델은 두 요청 사이에 아무것도 기억하지 않습니다. 안 보내면 냉장고와 상관없는 레시피가 옵니다.

6. unknown 을 any 로 바꾸지 마세요. any 는 타입스크립트에게 “검사하지 말라” 고 말하는 것입니다. 편해 보이지만 모델이 이상한 값을 보냈을 때 아무도 막지 않고 화면까지 흘러갑니다. unknown 이 불편한 것이 이 파일의 목적입니다.
