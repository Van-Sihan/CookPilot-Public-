쿡파일럿 학습 노트 · 05

키를 서버에 보내지 않고 AI 를 쓴다는 말

물어본 것 — “기능명세서에서 Gemini API 키를 서버에 전송하지 않는다고 했는데, 어떻게 서버에 전송하지 않고 API 키를 사용해서 AI 를 쓸 수 있는거야?”

여기서 말하는 “서버” 는 우리(쿡파일럿) 서버 입니다. 구글 서버가 아닙니다. 키는 브라우저 안에 담아 두고, 브라우저가 구글에 직접 요청을 보냅니다. 이 문서를 다 읽으면 키가 어디 저장되고, 누가 누구를 부르며, 이 약속이 통하지 않는 예외 한 곳(/api/chat)이 어디인지, 그리고 이 방식이 무엇을 포기했는지 알게 됩니다.

1부 · 기본 문법

“서버” 라는 말이 가리키는 것이 두 개입니다

웹 화면 하나가 돌아갈 때 컴퓨터는 최소 두 종류가 있습니다.

  • 브라우저 — 사용자의 크롬·사파리. 사용자의 기기 위에서 돕니다.
  • 서버 — 화면 파일을 내려 주는 컴퓨터. 쿡파일럿은 버셀(Vercel)에 있습니다.

그런데 AI 를 부르려면 세 번째 컴퓨터가 더 있습니다. 구글의 제미나이 서버입니다. 이것도 “서버” 입니다. 명세서의 “서버에 전송하지 않는다” 는 두 번째, 즉 우리 서버만 가리킵니다. 키를 구글에 안 보내면 AI 는 애초에 부를 수가 없습니다. 구글에는 반드시 갑니다.

localStorage — 브라우저 안에 값을 남겨 두는 서랍

localStorage 는 브라우저가 사용자 기기에 값을 문자열로 적어 두는 공간입니다. 탭을 닫아도, 컴퓨터를 꺼도 남습니다. 그리고 서버는 이 값을 볼 수 없습니다.

// 값을 적어 둔다
window.localStorage.setItem("my-key", "AIza...");

// 나중에 꺼낸다. 없으면 null 이 온다
const saved = window.localStorage.getItem("my-key");

// 지운다
window.localStorage.removeItem("my-key");
알아두면 좋은 것 · 쿠키와 무엇이 다른가

쿠키도 브라우저에 값을 남깁니다. 하지만 쿠키는 그 사이트로 요청을 보낼 때마다 자동으로 따라갑니다. 키를 쿠키에 담으면 사용자가 페이지를 한 번 넘길 때마다 키가 우리 서버로 갑니다. “서버에 안 보낸다” 는 약속이 저절로 깨지는 것입니다. 그래서 localStorage 를 씁니다. 이 값은 코드가 직접 실어 보내지 않는 한 아무 데도 안 갑니다.

브라우저에서 남의 서버를 직접 부르기

fetch 는 브라우저가 다른 주소로 요청을 보내고 답을 받아 오는 함수입니다. 보내는 주소는 우리 서버일 필요가 없습니다. 아무 주소나 됩니다.

// 브라우저 → 남의 서버. 우리 서버는 이 요청을 아예 모른다
const res = await fetch("https://example.com/v1/echo", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    // 신분증을 머리말(header)에 실어 보낸다
    "x-api-key": "AIza...",
  },
  body: JSON.stringify({ text: "안녕" }),
});

const data = await res.json();

이 요청이 지나는 길은 사용자 브라우저 → example.com 입니다. 우리 서버는 이 사이에 없습니다. 이것이 질문의 답 전부입니다.

2부 · 우리 코드에서는

① 키는 어디에 있는가

키를 담아 두는 파일은 딱 하나입니다.

lib/adapter/browser-api-key-store.ts:13 
/** 담아 둘 때 붙이는 이름표. 다른 값과 섞이지 않게 서비스 이름을 앞에 붙였다 */
const STORAGE_KEY = "cookpilot.gemini-key";

이름표에 cookpilot. 을 붙인 이유는, 같은 브라우저의 같은 도메인 안에서 다른 코드가 쓰는 값과 이름이 겹치지 않게 하려는 것입니다.

lib/adapter/browser-api-key-store.ts:28-38 
/**
 * 키는 이 브라우저 안에만 있고 서버로 보내지 않는다 — 요금제 안내에 그렇게 적어 두었다.
 * 그래서 쿠키가 아니라 localStorage 를 쓴다. 쿠키는 요청할 때마다 서버로 따라가 버린다.
 */
export const browserApiKeyStore: ApiKeyStore = {
  save(key: ApiKey) {
    window.localStorage.setItem(STORAGE_KEY, key);
    notify();
  },

주석에 판단 근거까지 적혀 있습니다. 쿠키를 안 쓴 것은 취향이 아니라 약속을 지키기 위한 선택입니다.

lib/adapter/browser-api-key-store.ts:46-55 
  load() {
    // 서버에서 화면을 그리는 동안에는 window 가 아예 없다. 그래서 먼저 막는다
    if (typeof window === "undefined") return null;

    const saved = window.localStorage.getItem(STORAGE_KEY);

    return saved ? (saved as ApiKey) : null;
  },

typeof window === "undefined" 줄이 중요합니다. Next.js 는 화면 일부를 서버에서 먼저 그려서 내려 줍니다. 그때는 브라우저가 아니라 서버에서 이 코드가 도는데, 서버에는 window 라는 것이 없습니다. 이 줄이 없으면 서버에서 오류가 납니다. 그리고 이 줄은 “키를 아는 쪽은 브라우저뿐” 이라는 사실을 코드로 보여 주기도 합니다 — 서버에서 이 함수를 불러도 항상 null 입니다.

② 브라우저가 구글을 직접 부른다

레시피를 받아 오는 실제 요청은 여기 있습니다.

lib/adapter/gemini-recipe-gateway.ts:7-8 (파일 머리 주석) 
* 브라우저에서 직접 부른다. 우리 서버를 거치지 않는 까닭은 요금제에 적어 둔 약속
* 때문이다 — 키는 이 브라우저 안에만 있고 서버로 보내지 않는다.
lib/adapter/gemini-recipe-gateway.ts:192-199 
res = await fetch(`${API_ROOT}/${model}:generateContent`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    /* 키를 주소(?key=)가 아니라 머리말에 싣는다.
       주소에 실으면 브라우저 기록과 중간 서버 로그에 키가 남는다 */
    "x-goog-api-key": apiKey,
  },
  body: JSON.stringify({ ... }),
});

API_ROOT 는 gemini-recipe-gateway.ts:29 에 있고 값은 https://generativelanguage.googleapis.com/v1beta/models 입니다. 우리 도메인이 아닙니다. 구글 주소입니다. 이 fetch 는 사용자 브라우저에서 구글로 곧장 나갑니다.

키를 ?key= 로 주소에 붙이지 않고 x-goog-api-key 머리말에 실은 것도 이유가 있습니다. 주소는 브라우저 방문 기록과 중간 장비의 로그에 통째로 남습니다. 머리말은 그렇지 않습니다.

실시간 음성(요리 중 말동무)도 같은 구조입니다. 다만 방식이 다릅니다.

lib/adapter/gemini-live-gateway.ts:86-88 
// 웹소켓은 머리말을 못 붙여서 키를 주소에 싣는다
const ws = new WebSocket(`${WS_ROOT}?key=${encodeURIComponent(apiKey)}`);

웹소켓(WebSocket) 은 한 번 연결해 두고 양쪽이 계속 주고받는 통로입니다. 소리를 실시간으로 흘려보내야 해서 fetch 대신 씁니다. 브라우저의 웹소켓 API 는 머리말을 붙일 수 없어서, 어쩔 수 없이 키가 주소로 갑니다. 이것도 우리 서버가 아니라 구글 서버로 가는 주소입니다.

③ 클린 아키텍처와 어떻게 맞물리는가

여기서 재미있는 점이 있습니다. 유스케이스에는 “제미나이” 라는 말이 한 번도 안 나옵니다.

lib/usecase/plan-recipe.ts:32-44 
/** 레시피를 만들어 주는 곳이 지켜야 할 약속. 진짜 구현은 lib/adapter 에 있다 */
export type RecipeGateway = {
  fromSpeech(clip: AudioClip, servings: number): Promise<GatewayRecipe>;

  /** 글로 적은 요리 이름으로 레시피를 만들어 온다 */
  fromDish(dish: string, servings: number): Promise<GatewayRecipe>;
  ...
};

이것은 인터페이스 입니다. “이런 이름의 함수가 이런 모양으로 있어야 한다” 는 약속만 적고, 실제 동작은 안 적은 것입니다. 유스케이스는 이 약속에만 기대서 일합니다.

lib/usecase/plan-recipe.ts:160-176 
export async function planFromDish(
  dish: string,
  servings: number,
  gateway: RecipeGateway,
  store: RecipeDraftStore,
): Promise<PlanResult> {
  const name = dish.trim();

  if (name.length === 0) return { ok: false, reason: "empty" };

  return finish(await gateway.fromDish(name, clampServings(servings)), store);
}

한 줄씩 봅니다.

  • gateway: RecipeGateway — 누가 레시피를 만들어 줄지 밖에서 받습니다. 이것을 의존성 주입 이라고 합니다. 필요한 도구를 스스로 만들지 않고 받아 쓰는 방식입니다.
  • name.length === 0 — 빈 글자면 다녀오지 않습니다. 헛되이 구글에 다녀올 이유가 없습니다.
  • await gateway.fromDish(...) — 여기서 구글에 다녀옵니다. 하지만 이 파일은 그것이 구글인지 모릅니다. 주소도 키도 이 파일에 없습니다.

진짜 구현을 끼워 넣는 자리는 화면(컴포넌트)입니다.

components/pick/pick-cards.tsx:112-114

  // 위에서 이미 키가 있는지 봤다. 없으면 여기까지 안 온다
  return geminiRecipeGateway(findSavedKey(browserApiKeyStore) ?? "", modelForSetup(setup));

브라우저에서 도는 컴포넌트가 localStorage 에서 키를 꺼내 geminiRecipeGateway 에 넘겨 게이트웨이를 만들고, 그것을 유스케이스에 건넵니다. 키를 아는 코드가 브라우저 안에만 모여 있는 이유가 이 구조입니다.

덤으로 얻는 것도 있습니다. 나중에 “서버를 거쳐 부르는 방식” 으로 바꾸고 싶어지면 RecipeGateway 를 만족하는 새 어댑터 파일을 하나 더 만들어 갈아 끼우면 됩니다. 유스케이스와 도메인은 한 줄도 안 고칩니다.

④ 예외 — 이 약속이 통하지 않는 곳이 한 군데 있습니다

명세서의 문장이 그대로 적용되지 않는 기능

FN11 AI 상담(/ask) 에서는 제미나이 키가 우리 서버로 갑니다. 예외입니다. 이유가 있습니다.

상담 기능은 RAG 방식입니다. RAG 는 질문에 답하기 전에 먼저 우리가 모아 둔 문서에서 관련 대목을 찾아 오고, 그 대목을 근거로 붙여 모델에게 답을 시키는 방식입니다. 그 “찾아 오기” 를 파인콘(Pinecone)이라는 검색 서비스가 합니다.

app/api/chat/route.ts:11-16 
* 이 자리가 있는 까닭은 파인콘 키다. 그 키는 우리 계정 것이라 브라우저에
* 내보낼 수 없다.
*
* **제미나이 키는 반대 방향으로 온다.** 사람이 시작 화면에서 넣어 둔 자기 키를
* 브라우저가 요청마다 실어 보낸다. 랭체인 체인이 서버에서 한 줄기로 돌아야 해서
* 이렇게 했다 — 받은 키는 그 요청 안에서만 쓰고 담아 두지도, 적어 두지도 않는다.

정리하면 이렇습니다. 파인콘 키는 우리 회사 계정 것이라 브라우저에 내보낼 수 없습니다. 내보내면 누구나 개발자 도구로 꺼내 우리 계정에 요금을 태울 수 있습니다. 그래서 검색은 반드시 서버에서 해야 하고, 검색과 답 만들기가 한 줄기로 이어져 있으니 제미나이 키도 같이 서버로 와야 합니다.

브라우저 쪽 코드도 이 사실을 숨기지 않습니다.

components/ask/ask-shell.tsx:146-153 
const res = await fetch("/api/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  /* 키를 함께 보낸다. 우리 서버를 한 번 거치지만 그 요청 안에서만 쓰이고
     어디에도 담기지 않는다 — 화면 아래에 그렇게 적어 두었다 */
  body: JSON.stringify({ question: text, history: before, chatId, apiKey }),
});

주소가 /api/chat 입니다. 앞에 도메인이 없는 주소는 지금 이 사이트의 서버를 뜻합니다. 즉 이 요청은 확실히 우리 서버로 갑니다. 키가 body 안에 실려 있습니다.

서버가 그 키로 무엇을 하는지도 봅니다.

app/api/chat/route.ts:84-104 
// 모양만 도메인에 물어본다 — 맞는 키인지는 실제로 써 봐야 안다

  readHistory(bag.history),
  langchainRag(read.key),
  supabaseChatLog,

read.key 는 langchainRag(...) 에 그 자리에서 넘겨지고, 이 함수가 끝나면 사라집니다. 파일에도 데이터베이스에도 적지 않습니다. “저장하지 않는다” 와 “전송하지 않는다” 는 다른 말입니다. 상담 기능은 앞의 것만 지킵니다.

그래서 명세서 문장은 이렇게 읽는 것이 정확합니다.

  • 레시피 만들기 · 냉장고 추천 · 요리 중 음성 — 우리 서버에 전송하지 않습니다. 브라우저가 구글을 직접 부릅니다.
  • AI 상담(FN11) — 우리 서버에 전송합니다. 다만 그 요청 안에서만 쓰고 저장하지 않습니다.

⑤ 이 방식이 포기한 것

공짜는 없습니다. 두 가지를 내줬습니다.

첫째, 기기를 바꾸면 키를 다시 넣어야 합니다.

docs/deploy/vercel.md:267 
| Gemini 키는 브라우저마다 | 서버에 저장하지 않는다. 기기를 바꾸면 `/start` 에서 다시 넣어야 한다 |

당연한 결과입니다. localStorage 는 브라우저 하나에 묶인 서랍입니다. 회사 컴퓨터 크롬에 넣은 값은 집 노트북에도, 같은 컴퓨터의 파이어폭스에도, 시크릿 창에도 없습니다. 서버에 안 담기로 한 순간 기기 간에 옮길 방법이 없어집니다.

둘째, 사용자 본인 키만 이렇게 쓸 수 있습니다.

브라우저에서 도는 코드는 사용자가 전부 들여다볼 수 있습니다. 개발자 도구의 네트워크 탭을 열면 x-goog-api-key 머리말이 그대로 보입니다. 그러니 이 자리에 우리 회사 계정의 키를 넣는 것은 절대 안 됩니다. 넣는 순간 아무나 꺼내 쓸 수 있고, 요금은 우리가 냅니다.

지금 구조가 성립하는 이유는 딱 하나 — 그 키가 사용자 자신의 키라서, 노출돼 봐야 자기 것이기 때문입니다. 반대로 파인콘 키는 우리 것이라 서버 뒤에 숨겨야 했고, 그래서 /api/chat 이 생긴 것입니다. ④ 의 예외는 예외가 아니라 같은 원칙에서 나온 다른 결론입니다.

알아두면 좋은 것 · 판단 기준 한 줄

키가 누구 계정 것인가로 갈립니다. 사용자 키면 브라우저에 두고 직접 부릅니다. 우리 계정 키면 서버 뒤에 숨기고 서버가 부릅니다. “브라우저에 두면 위험하다” 가 아니라 “남의 지갑이면 위험하다” 입니다.

실험 1 · 키가 정말 브라우저 안에만 있는지 눈으로 보기

npm run dev 로 띄우고 /start 에서 키를 넣습니다. 그다음 개발자 도구(F12) → Application 탭 → 왼쪽에서 Local Storage → http://localhost:3000 을 엽니다. cookpilot.gemini-key 라는 줄이 보이고 값이 그대로 들어 있습니다. 이름표는 lib/adapter/browser-api-key-store.ts:13 에서 정한 그 문자열입니다.

이 값을 그 자리에서 지우고 화면을 새로 고쳐 보세요. 키를 넣으라는 화면으로 돌아갑니다. 같은 파일 :74 의 storage 이벤트 덕분에, 다른 탭을 열어 두었다면 새로 고치지 않아도 반응합니다.

실험 2 · 요청이 어디로 나가는지 확인하기

개발자 도구 → Network 탭을 켠 채로 /pick 에서 요리 이름을 적어 레시피를 만들어 보세요. 목록에 generativelanguage.googleapis.com 으로 가는 요청이 하나 뜹니다. localhost:3000 이 아닙니다. 그 줄을 눌러 Headers 를 보면 x-goog-api-key 에 내 키가 실려 있습니다.

이번엔 /ask 에서 무언가 물어보고 같은 탭을 보세요. 이번에는 localhost:3000/api/chat 으로 가는 요청이 뜨고, Payload 안에 apiKey 가 들어 있습니다. ④ 에서 말한 예외를 눈으로 확인하는 것입니다.

실험 3 · 일부러 틀린 키를 넣어 보기

Local Storage 의 cookpilot.gemini-key 값을 AIzaSyDUMMY_WRONG_KEY_1234567890abcdefghij 처럼 모양만 그럴듯한 가짜로 바꾸고 레시피를 만들어 보세요. 구글이 400 이나 403 으로 거절합니다. lib/adapter/gemini-recipe-gateway.ts:135 의 reasonFor 가 그 상태 코드를 "key" 라는 우리 낱말로 바꾸고, 화면은 “키를 다시 넣어 달라” 고 안내합니다.

여기서 중요한 점 — 키가 맞는지 판정하는 것은 우리 코드가 아니라 구글입니다. 우리 서버는 이 판정에 아예 끼지 않습니다. 키를 안 갖고 있으니 판정할 방법도 없습니다.

실험 4 · 다른 브라우저에서 열어 보기

크롬에서 키를 넣어 둔 상태로, 같은 주소를 시크릿 창이나 다른 브라우저에서 엽니다. 키가 없다고 나옵니다. 로그인 상태는 따라오는데 키만 안 따라옵니다. docs/deploy/vercel.md:267 에 적힌 제약을 그대로 겪는 것입니다. 불편해 보이지만, 이것이 “서버에 저장하지 않는다” 의 대가입니다.

헷갈리기 쉬운 점

1. “서버에 안 보낸다 = 아무 데도 안 보낸다” 가 아닙니다. 구글에는 반드시 갑니다. 안 보내면 AI 를 쓸 방법 자체가 없습니다. 문장의 뜻은 “중간에 우리를 안 거친다” 입니다.

2. “전송하지 않는다” 와 “저장하지 않는다” 는 다른 약속입니다. /api/chat 은 전송은 하고 저장은 안 합니다. 두 낱말을 섞어 쓰면 코드와 명세서가 어긋나 보입니다.

3. localStorage 에 넣은 값은 암호화되지 않습니다. 그냥 글자 그대로 놓여 있고, 그 브라우저를 만질 수 있는 사람은 누구나 봅니다. 이 방식이 괜찮은 이유는 안전해서가 아니라 그 키의 주인이 바로 그 사람이기 때문입니다.

4. lib/usecase/ 안에서 fetch 나 주소를 찾지 마세요. 유스케이스에는 없습니다. 일부러 없앤 것입니다. 실제로 어디로 나가는지 알고 싶으면 항상 lib/adapter/ 를 보세요.

5. 웹소켓 키가 주소에 붙은 것을 실수로 오해하지 마세요. gemini-live-gateway.ts:88 의 ?key= 는 브라우저 웹소켓이 머리말을 못 붙이는 제약 때문입니다. 그 주소는 구글 주소이고, 우리 서버 로그에는 남지 않습니다.
